## Context

The initial uncommitted proposal targeted one Linux host and a private read-only observer. The operator changed the **requested MVP function scope** to all filesystem read/write operations and Docker Compose deployment of the MCP server and each SSH server. The operator subsequently **confirmed two mandatory deployment modes**: (A) **single-engine, multi-container Compose** for local development/E2E; and (B) **multi-host, per-host Compose** for actual production-like private deployment, with the control plane and at least two SSH servers on independently administered Linux Docker hosts. Both modes are MVP deliverables, not optional alternatives. The topology choice is confirmed; component design, privileged operations and production release are still subject to separate approval.

Current main implements **nine public MCP tools** (the full eight-tool filesystem contract below is a **future MVP target**, not current registry state), including typed `fs_stat`, `fs_read`, `fs_mkdir` and `fs_write`, but the latter two are create-only. The broader `fs_list`, `fs_search`, `fs_move`, `fs_delete` contract and overwrite/append are **not implemented end-to-end**. The normative `docs/mcp-api.md` lists all eight as an intended contract; it separately explains which are already available. Existing `deploy/compose/compose.yaml` covers the MCP control plane, Ledger, admin approval and optional Tunnel, **not production SSH server containers**. The `mcp` service has a broad `ssh_egress` Compose attachment with no enforced per-host destination allowlist in that file, and the default control-plane image `ssh-over-mcp:phase6b` is a mutable **tag** rather than a fixed digest; neither can be silently treated as satisfying the new multi-host security gates. Existing host-agent containment requires separate manager authority and delegated cgroup v2, plus ADR0007's exact ForceCommand-to-capability launcher; putting `sshd` in an ordinary Docker container does not prove this contract.

Phase 5 approval/audit, Phase 6 private control-plane Compose and Phase 7A Linux E2E have implemented portions. Exact main `push` run [39882670723](https://github.com/zhangyuz/ssh-over-mcp/actions/runs/39882670723) was accepted at 11/11; that run cannot certify new Compose SSH target isolation or complete read/write semantics.

The historical complete-v1 roadmap includes additional roles and administrative services. A restricted-path private RW trial still cannot be described as full v1. Issue [#259](https://github.com/zhangyuz/ssh-over-mcp/issues/259) addresses the **new macOS test-orchestrator** trusted-native UID502/APFS/protected staging requirements; Issue [#256](https://github.com/zhangyuz/ssh-over-mcp/issues/256) defers Linux provenance C/D.

## Proposed decision

1. Replace the original observer/single-native-host proposal with a **private read/write product MVP supporting BOTH deployment topologies**: **Mode A (development/E2E)**: one disposable Linux Docker Engine, one Compose project or explicitly paired Compose overlays, a control plane and at least two separated SSH containers. **Mode B (actual deployment)**: one approved control-plane Linux host running MCP/Ledger/approval with its own Compose project, and **at least two distinct remote Linux hosts**, each independently running its own SSH target Compose project/container. No single-machine result can be counted as distributed deployment acceptance. Both modes share the same eight-tool API, server-owned static `rw-operator` profile, logical host aliases (`node01`, `node02`), per-host policy, independently pinned SSH host keys and exact audit/approval protocol.
2. Include all eight typed filesystem capabilities in the product MVP: `fs_list`, `fs_stat`, `fs_read`, `fs_search`, `fs_mkdir`, `fs_write` with explicit create/append/replace modes, `fs_move`, `fs_delete`. **Before implementation, freeze the versioned four-part contract in design §2a**: (a) trusted **SMCP v2 central subtree authorization snapshot, monotonic policy epoch and per-node host authorization with pre-traversal deny pruning and central results recheck**; (b) explicit **Host Policy v5 deny-subtrees** schema and v3/v4 rejection/rollback; (c) host-bound **global Operation ID, durable remote operation journal/commit receipt, Ledger correlation and UNKNOWN/no blind retry**; (d) deterministic typed search/list/mutation schema with conditions/error states. Each capability must have server, both policy layers, typed SSH protocol, safe bounded outputs and real host tests. These are proposals, **NOT_IMPLEMENTED/NOT_RUN**; existing SMCP v1, Host Policy v3/v4 and approval consumption do not provide them. Existing no-overwrite/create-only semantics remain unchanged.
3. “All reads/writes” is **all specified operations within explicitly allowed data roots**, not arbitrary host-wide access, arbitrary shell, sudo/root, service management or Docker control. Only non-recursive deletion of approved regular files/empty directories is within the first written contract; broader recursive deletion requires explicit additional design, operator decision and security acceptance. Fixed allowlisted `ssh_exec` may remain a separate capability; `ssh_shell` remains denied by default.
4. Reuse the existing `deploy/compose/compose.yaml` control-plane security architecture; provide a **development Compose overlay** that co-locates two independent SSH services on the disposable E2E Engine, plus a **separate deployable SSH-target Compose project** that is installed and operated independently on *each* real SSH Linux host. No `docker compose` command is assumed to orchestrate other remote Engines. Across real hosts, only an **operator-approved private routed network/overlay** with outbound MCP→SSH TCP/22 and ingress restricted to the control-plane endpoint may connect them; the exact connectivity provider and private addresses remain operator-owned. Per-node inventory aliases, credentials and host-key pins are fixed server-side. No public SSH or origin ports, Docker socket, `privileged`, host PID/net namespace, broad root mounts or host cgroup write shortcuts. **Release is blocked** unless delegated cgroup/manager/host-agent separation, limited privilege, ForceCommand, independent volume boundaries and private inter-host network ACLs are independently demonstrated on *each* participating Linux Engine.
5. Permit **separate product trial release review** from the ADR0019/UID502/APFS/protected Mac staging milestone **only after explicit written acceptance of this ADR**. Keep the required canonical trusted-main no-network Level-3. **Acceptance requires BOTH** an actual disposable single-engine E2E and an authorized **multi-host Compose E2E** covering at least one control-plane host plus two remote SSH hosts, cross-host reads/writes, host-key mismatches, network partition, host loss/restart, audit, approval, recovery and SSH ingress policy. The legacy Native Level-3 and a local 8-tool simulation cannot substitute for this distributed acceptance; absent permissions or isolation keep release HOLD.
6. Preserve all authn/SSH boundaries: static profile and inventory; no model-selected address/SSH identity/key/profile; host-key pinning; deny override and independent host-side policy; approved roots/OS permissions; exact approval keyed by tool/host/paths/mode/content/**operation ID/policy epoch**, required Ledger audit before side effects and a **separate durable remote mutation journal/commit witness**, fail-closed uncertain outcomes (including no blind manual reapproval/re-execution), fixed artifact/image/launcher origins and independent source review. **Parent allow is not descendant allow:** list/search must authorize each traversed path and each returned name/content, prune denied subtrees before scanning, and paginate only visible authorized results (no hidden-name/count/cursor disclosure). The `rw-operator` profile must **default-deny all `ssh_exec` filesystem mutation equivalents**; adding a command to the allowlist never bypasses typed FS authorization/approval/audit. A separately reviewed ADR and operator approval are needed for any equivalent exec mutation. Both modes must explicitly constrain **MCP egress to approved destination identity/ports** and prove **network deny** to arbitrary endpoints, not rely on the existing broad `ssh_egress: {}` connection; production image references must be pinned/verified by digest rather than the current default tag. Do not change historical Compose semantics without a separately reviewed migration plan and regression tests.
7. Keep #259 source/root/runtime/clock/verifier/material and Mac native admissions open. Keep #256 Linux C/D deferred until its existing Mac condition is genuinely met. Shipping this Compose product MVP is **not** the Mac readiness milestone, and not completion of full v1.
8. Neither this ADR nor the scope request grants permission to run Docker/Compose, change a host user or cgroup, mount real credentials, install unsigned runtimes, modify Cloudflare accounts, dispatch privileged tests, merge a PR, or publish a release. The implementation plan uses isolated feature PRs, independent review, exact SHA verification and per-environment approval.

## Alternatives and trade-offs

- **Selected / both mandatory:** single-engine multi-SSH Compose as a fast reproducible developer/E2E fixture **and** distinct per-host Compose installations over private routed connectivity for actual deployment. Shared schemas and tests limit drift but distributed operations need independent network, credential, host-key and recovery evidence.
- **Rejected: local-only Compose MVP.** Easier to ship, but cannot satisfy multi-host operational behavior or prove network partition, firewall scope and independently administered remote nodes.
- **Rejected: native sshd-only remote hosts.** Already closer to the existing native host-agent model, but does not meet the request that **each SSH server be deployed by Docker Compose**. It may inform an explicitly separately approved contingency, never silently replace the selected topology.

## Consequences and security impact

The read/write attack surface expands materially compared with read-only observer. The current host-agent dispatches typed filesystem operations before manager connection/workload identity drop, and the current central policy approval binding only covers one normalized path without destination/mode; **both are unresolved high-risk implementation gaps** and mandatory security blockers for the new write modes. Initial `fs_move` **may become generally available for regular-file moves only after M2d double-path authorization, one-shot exact approval, Ledger/audit schema migration, isolated positive/negative acceptance and pre-merge exact-HEAD Native Level-3 PASS**, and `fs_delete` has the **same hard prerequisite**; otherwise both stay UNAVAILABLE/DENY **in production**. To avoid circular E2E dependencies, the exact candidate SHA/image digest can exercise test-only capabilities in explicitly operator-authorized, disposable isolated Mode A and Mode B environments with synthetic data and independent identities, never on production connections. This test authorization is not a release/production feature toggle or merge approval. **All directory moves stay disabled** until a separate proof of concurrency-safe empty-directory checking + atomic relocation, including adversarial insertion/reparenting races, exists. Nonempty directory moves remain denied regardless, avoiding reparenting denied descendants. The methodology also requires **exact-PR-SHA guest-native Level-3 before merge** for these changed security boundaries, separate from the canonical new-main 11/11 after merge. An existing SSH target compromised during arbitrary user-content processing must not reach sibling data volumes, admin sockets, Ledger DB/key, host cgroups or Docker daemon. Compose service separation alone is not equivalent to hardened kernel confinement. Every newly exposed mutation requires exact policy, resource bounds, atomicity, idempotency/approval-consumption and audit refusal proofs. No privileged shortcut is acceptable to make Compose startup green.

Every user at the same private origin shares the **static SOM identity**, not per-human attribution; Portal can restrict entry, but the application cannot claim per-user audit separation. If materially different permissions are necessary, operate separate origin/profile/credential and independently validate its policy. Per-host roots and independent host keys are not user-supplied.

Onboarding must be real **in both modes**: reproducible operator-approved Compose images/config, independent per-host Compose project/config and SSH host-key lifecycle, SSH contained identities, private address mapping/firewall/route ownership, eight-tool positive/negative tests across at least two separate SSH Engines, inter-host network loss/restart, credential revocation, and coordinated consistent control-plane+remote-volume backups. A local two-container test, a test-only sshd fixture, or CI with Native Level-3 skipped cannot serve as multi-host release evidence.

## Additional implementation-blocking protocol decisions (Proposed)

- **P1 — Authorize before traversal, not after:** an authenticated **SMCP v2** snapshot of the effective central subtree policy, `policy_epoch`/digest/expiry and an explicit revoke/activate acknowledgement barrier coordinates with a **Host Policy v5** deny-subtree engine; both layers check every traversal node before entering it, and the control plane rechecks each authorized result on the same epoch. Old/stale snapshot, unsigned policy, rollout to only one host or ambiguous rule rejects the whole request. Parent allow does not override child deny; listing/search cursors/counts cannot leak denied subtree names. Current SMCP v1 per-request path authorization is insufficient.
- **P2 — Formal Host Policy v5 schema and compatibility:** versioned per-capability allow roots/deny-subtrees with **deny the subtree root plus all descendants**, monotonic host policy epoch and exact signed digest. v3/v4 remain valid for their existing limited operations but must reject new list/search/mutation modes; unknown fields/version, rule conflicts, rollback and epoch drift fail closed. No silent v1/v3/v4 downgrade and no inferred deny just from allow-roots alone.
- **P1 — Distributed idempotent mutation protocol:** unique server-minted `operation_id` bound to exact approval/host/path/mode/content/target precondition, durable per-SSH-host journal state, **verifiable committed receipt**, and control-ledger/audit correlation. A consumed approval ID or v1 request ID is not an exactly-once guarantee. Post-effect/pre-receipt crashes, partition, untrusted journal, duplicate IDs, or human reapproval of the same append/write/move/delete require UNKNOWN quarantine and proof-based reconciliation. If no safe durable state/commit evidence and anti-duplicate guarantee exists for an operation mode, leave the mode disabled; no auto retry or blind manual new approval.
- **P2 — Typed API schema freeze (typed API):** `fs_search` basename-only restricted `*`/`?` glob or case-sensitive UTF-8 byte-literal content search, strict invalid-encoding handling, filtered stable UTF-8 byte sorting and epoch-bound snapshot cursors. `fs_write(create)` requires target absence, `replace/append` require a host-bound old generation/inode/size/SHA256 precondition and operation journal; failure states and commit receipt must be stable and non-sensitive. New mode schemas cannot silently alter already deployed create-only v1 requests. Numeric bounds and enum values in the spec are provisional until independently frozen.

The four contract decisions are implementation/release **HOLDs** until designed, adversarially tested, independently reviewed and separately approved; they do not authorize container/network operations or make any new function live.
