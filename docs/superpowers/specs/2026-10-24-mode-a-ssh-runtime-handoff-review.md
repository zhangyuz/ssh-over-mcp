# Mode A real SSH target bootstrap and privilege contract — review candidate

**Status: PROPOSED / HOLD; not approved, not runnable, not deployed.** This is a concrete security review input for PR #342, *not* a permission to start Docker, build/pull an image, mount host cgroups, generate host keys, install sudo rules, or alter host privileges. No SSH target image or startup binary is delivered by this proposal. The existing Compose overlay remains deliberately render-only. A01–A03 and Mode B A15–A18 are NOT_RUN.

## Immediate feasibility conflict (must resolve before implementation)

Both `node01` and `node02` currently declare `cap_drop: [ALL]`, `no-new-privileges:true`, and no command/entrypoint/user/manager service. The checked-in control-plane `Dockerfile` installs only the MCP client/server application; it does **not** install/configure an sshd, sudo, PAM/login account, host-agent launcher or containment manager. Therefore it is unsafe to supply arbitrary SSH image references and attempt to run these nodes as if the overlay were complete.

The accepted [ADR0007](../../decisions/0007-host-agent-capability-launcher.md) requires `sshd` to invoke an exact no-argument sudo handoff into a root-owned launcher, which (before Python application import) joins an approved `host-agent-source` delegated cgroup, drops permanently to the configured host-agent UID/GID, and retains **only** CAP_SETUID and CAP_SETGID. In the current container proposal, `no-new-privileges:true` prevents the account-to-root sudo handoff, while dropping all capabilities eliminates the required credential transitions. The Compose fields are **incompatible with assuming this existing launcher works**. Disabling NNP, adding capabilities, mounting a writable cgroup hierarchy or relying on a root image by default is not an acceptable workaround. This needs an independently reviewed revised decision/ADR with explicit operator authority.

The checked-in **`deploy/ssh-target/sshd_config.proposed`** is an intermediate *OpenSSH configuration proposal only*: it copies the locked-down requirements from the already-tested disposable-native guest, but it has no associated approved image, user, private-key volume, server-managed authorized-keys source, signed installer, sudo policy or launcher compatible with a container. The `AllowUsers ssh-over-mcp-e2e-host` entry is **E2E-only** because the existing launcher explicitly validates that identity; it must be replaced by a separately reviewed, container-specific fixed identity together with a matching launcher build and sudoers contract before any deployment. It deliberately keeps public-key-only authentication, no root login, no PTY, TCP or Unix-socket forwarding (explicit `DisableForwarding yes` **and** `AllowStreamLocalForwarding no`), user rc or user env; fixed sudo ForceCommand; and a single read-only host-key file. It does not assert Linux `sshd -t` validity, actual socket listening, host-key trust, or session enforcement. `AuthorizedKeysFile /etc/ssh/authorized_keys/%u` requires a **separately verified, immutable per-node** authorized-key source; it is **not present in the current overlay**. Do not bake any real credentials into a candidate image.

## Candidate security boundary and lifecycle (decision required)

1. **Operator-sourced immutable image:** base OS, Python/OpenSSH/sudo packages and trusted launcher source/build artifacts pinned to independently verified digest/signature and subject to build provenance review. Explicit source hash, signer/CA and revocation/upgrade path. Cannot use untrusted, synthetic, mutable or tag-only image refs.
2. **Node-specific identity assets:** provision one SSH host key per target via approved out-of-band process, verify owner/mode and server-side pinned public key before the first connection; independent data and authorized-public-key assets (no node-to-node reuse). Fail readiness on missing/rotated/untrusted keys; do not accept SSH fingerprints from model arguments.
3. **Minimal process authority:** document exact process tree (`sshd` master/session, fixed launcher, manager service, host-agent, unprivileged workload), initial UID/GID/capabilities, inherited groups/fds, runtime `no_new_privs` boundaries, and how a fixed sudo handoff can work *without a general privilege escape*. A container image running as root or cgroup enabled by itself is not proof. Preserve no generic sudo, no `SYS_ADMIN`, Docker socket, host PID/net, unrestricted host root or cgroupfs.
4. **Cgroup v2 kernel delegation:** an explicit operator-approved cgroup subtree scoped to each node, with owner, controller enablement (`cpu`,`memory`,`pids`), writable endpoints, verified exact membership and restricted manager-client Unix socket. No writable host cgroup root; the workload cannot migrate itself, change ancestor controls, or access the manager authority. Test the actual container namespace and cgroup mount—not a VM-native substitute. A manager in another service/container needs separate peer-identity and namespace review.
5. **FD-anchored typed FS operations:** current `host_agent.cli._run_filesystem_request` precedes `connect_authenticated_containment_manager` and does not inherit the `ssh_exec` per-request workload identity/cgroup. Before real mutation/full typed FS E2E, explicitly design/review bounded FD-anchored FS execution under an independently verified non-root identity, memory/time/IO/FD limits, audit ordering and crash `UNKNOWN` semantics. Existing create-only success under a privileged host-agent is not sufficient.
6. **Startup/ready semantics:** image must fail startup if any trusted asset, cgroup delegation, manager identity/socket, host policy, UID isolation or SSH config validation fails. Only after actual authorized Linux-Engine startup and hostile probes may `ready` become true. Current Compose shape/static validators must continue to report `deployment_ready=false`, regardless of digest appearance.

## Deployment authority and evidence gates

**Before any `docker compose up`, `pull` or `build` (even a disposable test):** operator identifies the specific disposable Linux Engine, Docker API authority boundary, approved candidate image source and isolated/ephemeral keys, and separately approves that limited action. Do not touch `yuz.local`'s Docker daemon or privileged host without that approval. If selected architecture changes ADR0007's trust/privilege boundary, produce a separate proposed ADR and independent security review **before** implementation/promotion.

**Actual Mode A acceptance A01–A03:** on one approved disposable Linux Engine use *two* host-key-distinct sshd/host-agent/manager nodes under exact candidate image digest. From the origin MCP exercise two genuine pinned host-key SSH sessions and positive typed read/read-only probes; negatives must include wrong/rotated host key, unauthorized SSH command, PTY/X11/port forwarding, no manager, cgroup delegation failure, data/host-key isolation, cross-node network connections, startup/restart/cleanup, Ledger audit-before-effect failure, and workload UID/capability/cgroup assertions. M2 full RW remains separately blocked on P1/P2 protocol freeze. Collect immutable image/source/config hashes, shell-free test commands, exact-head native Level-3 and independent adversarial review. Mode B uses **three distinct Engines** and has its own A15–A18 real private-network/cgroup/firewall/host trust evidence. No static or mocked evidence is a live PASS.

## Review questions for the next decision

1. Is a constrained single-container `sshd`/manager/bootstrap compatible with ADR0007, including an independently delegated per-node cgroup and exact sudo launcher? If not, is a two-domain per-node architecture the narrowest safe alternative? Neither option is currently approved.
2. What **minimum** initial privilege, `no_new_privs` transition and cgroup mapping is demonstrably sufficient? Which kernel/OCI negative proof must fail when the requested capabilities are absent? Explicitly reject an unbounded root or writable ancestor.
3. Who attests the image, authorized keys, SSH host key source, UID/GID and manager socket ACL? How does rollback keep authorization revoked and preserve isolated host keys?
4. Does typed FS require a separate restricted helper/service for each operation so its containment is no weaker than `ssh_exec`? How is UNKNOWN prevented from double-applying mutations?

**Next unblocked engineering step:** obtain independent security/architecture review of this proposal and explicit acceptance of the resulting minimal-privilege ADR; only then implement the actual target image/startup and run approved disposable-Linux positive/hostile probes. Until then #342 remains DRAFT and no image/run/host operation is authorized.
