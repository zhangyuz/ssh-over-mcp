# PR #342 — Mode A executable-boundary candidate and no-NIC Docker Level-2 plan

**Status: PROPOSED — DESIGN/OFFLINE TESTS ONLY; P1 execution architecture not accepted.** Follows independent [review #6398447123](https://github.com/zhangyuz/ssh-over-mcp/pull/342#issuecomment-6398447123). The operator approved QEMU/HVF **as design choice**, not VM boot, Docker API/build/pull, keys, capabilities, cgroup or host-network actions. The [reviewable JSON contract](../../../deploy/ssh-target/mode-a-execution-contract.proposed.json) is a proposed set of expectations for tests, **not** a Compose override or a runtime launcher. Existing Compose `cap_drop: ALL` and `no-new-privileges:true` remain unchanged and intentionally non-runnable.

## Narrowest executable split to review

**One sshd + one separate manager per node, two nodes, one isolated guest Engine.** The manager must not share the sshd container's **mount/user** namespace. The agent retains `CAP_SETUID` and `CAP_SETGID`, which can impersonate UID0 *within its user namespace*. Therefore a manager writable cgroupfs mount or privileged manager FD inside that same container would be accessible to a compromised agent, regardless of ordinary DAC file mode. Separate OCI mount/user isolation and manager's narrow Unix socket API are mandatory; a second process under a different UID in the same container is insufficient.

Proposed **identity namespace**: QEMU isolated guest controls the Engine; each sshd and manager has private mount/user namespace, not host userns. Explicit mapping in each OCI spec must be recorded from `/proc/<pid>/uid_map` and `gid_map` before this design can be accepted. Node-local *candidate* numeric UIDs/GIDs: SSH account `2201:3201`, host agent `2202:3202`, workload `2203:3203`, manager `2204:3204`, manager-client supplementary group `3299`. Values must be proven non-overlapping and correctly mapped in real guest; host key and cgroup writer ownership must be verified. Different nodes get separate file/data/key identities; never reuse private volumes, authorized keys or sockets. Production mapping remains separate.

The candidate four-capability sshd bounding set is **NOT asserted sufficient**. Only workload gets NNP=1; this is an **irreversible** Linux privilege restriction: NNP cannot be cleared within that process tree.

**Manager fail-closed prerequisites:** separate mount/user namespace, distinct per-node cgroup delegation with only `cpu,memory,pids` controllers, independent trusted guest-root setup (not target-supplied script), read-only ancestors, no writable cgroupfs or manager-side socket mount in sshd except precisely authenticated socket endpoint, verified peer UID/GID/SO_PEERCRED. If shared PID namespace makes the manager a container escape or fails to translate target PID safely, **STOP and review another separation** rather than using `pid: host` or broad privileges. No `privileged: true`, `SYS_ADMIN`, generic sudo, host rootfs, Docker socket or host cgroup-root escape.

## Two P1 handoffs — one deliberately narrow protocol extension

**P1-A, launcher source cgroup:** Accepted **ADR0007** remains the managed-host contract: its native launcher currently writes its own PID into `host-agent-source/cgroup.procs`. The *proposed OCI profile differs*: sshd/launcher/agent **must not mount writable cgroupfs**. Before dropping root, the trusted fixed launcher opens a *fresh root-phase* AF_UNIX connection to **its own node manager**, sends `move_source_self` with its **self-opened pidfd** using `SCM_RIGHTS` and no caller-supplied target PID or path, and waits. The manager checks `SO_PEERCRED` captured at connect time against independently verified **namespace-mapped root launcher identity**, verifies the passed pidfd refers to that same peer in the shared node PID namespace, checks immutable launcher provenance and its current membership, and migrates *only that peer* to the fixed node-local `host-agent-source`. Manager rechecks `/proc` PID identity and exact cgroup membership, then ACKs. Launcher independently verifies `/proc/self/cgroup`, **closes the root-phase control FD**, sets groups and drops to the trusted two-cap nonroot agent *before application import*. A **new post-drop socket** must be opened for later manager RPC: Linux `SO_PEERCRED` is a connection-time snapshot, so reusing a pre-drop root-authenticated FD across the transition is forbidden. Unmapped peer credential (including overflow UID), missing pidfd or manager, changed PID, wrong source/target cgroup or timeout => **fail closed before import**. This is a **proposed OCI-specific replacement** for ADR0007's root-owned direct cgroup write, requiring **independent ADR approval**, not a silent edit of accepted managed-host code.

**P1-B, request child PID identity:** Current `AttachRequest` in `src/ssh_over_mcp/host_agent/containment_manager.py` has **only integer `pid`**; even a correct `SO_PEERCRED` on the agent connection does not authenticate that unrelated integer. The OCI transport therefore needs a **minimal versioned attach extension**: the trusted agent forks the child **behind an unreleased start barrier**, obtains/pins a pidfd while the child remains alive and unreaped (or uses `clone3(CLONE_PIDFD)` if required), and sends that descriptor via `SCM_RIGHTS` on its **fresh post-drop** authenticated AF_UNIX connection. The manager accepts no plain integer-PID attach; it checks the peer's `SO_PEERCRED` UID/GID/PID with *verified `uid_map`/`gid_map` and shared same-node PID namespace*, derives target PID from pidfd/kernel observations in **manager's** PID namespace, rejects mismatches with request metadata, verifies `/proc/<pid>` UID/GID, starttime, direct-child parentage with that authenticated agent, currently pinned pidfd and node-local `host-agent-source` cgroup, and holds the descriptor through attach. It writes only that verified live target PID to the node's **request** `cgroup.procs`, rechecks the same pidfd identity + `/proc/<pid>/cgroup` request membership and only then ACKs; parent releases the barrier **after ACK** (the attach-before-release invariant). Refuse stale/dead pidfds, child exit/reap, PID reuse or recycle, sibling-node processes, unmatched mappings, any unsigned identity hint or non-atomic race. Since `cgroup.procs` takes a **numeric PID rather than a pidfd**, a pidfd plus before/after checks alone is **not a proven atomic race-free attach**; actual guest-kernel PID lifetime/registration behavior and a hostile PID-exit/reuse test must demonstrate no wrong-process migration. **If that cannot be proved, STOP and redesign**; never downgrade to integer-only attach or broaden the manager namespace/privileges to get a GREEN test.

**Minimality:** add exactly **one** narrowly typed `move_source_self` RPC and **one** pidfd-bearing attach variant for the OCI manager transport after design acceptance. Preserve the existing deployed integer-PID protocol unchanged until then; no generic PID migration, arbitrary cgroup destination, raw FD accessor, extra privileged service, broad sudo rule or new host Docker orchestration. This document and the JSON contract remain **design-only**: `source_to_request_attach_ack_verified=false`, `userns_uid_gid_maps_runtime_proved=false`, `cgroup_delegation=UNPROVEN_STOP`, and `runtime_execution_authorized=false`.

## No-NIC Level-2 fixture without changing Native Level-3

B direction selected: **reuse the trusted-main QEMU/HVF x86_64 no-NIC, no-host-sharing security pattern**. Build a *separate reviewed Level-2 guest media/boot plan*, not a modification to the existing trusted Native Level-3 provider. Proposed guest QEMU command must be independently verified for **`-nic none`**, zero other QEMU network devices/backends, no host bind/socket/share, fixed guest image SHA256, finite vCPU/memory/disk quotas, read-only externally verified payload/media, bounded serial-only result output, and destruction of VM overlay/media after each test. The earlier Lima 2.2 `som-mode-a-ubuntu2604` remains **STOPPED and untouched**.

**Offline Docker/software delivery:** a *separately authorized isolated build/fetch environment* uses the exact Canonical-pinned base plus standard **Ubuntu signed APT** indices and pinned required direct OpenSSH/sudo/Python/Docker Engine versions. Record resolved installed packages and package SHA256, source HEAD, reviewed Dockerfile, guest Docker daemon binary source and final immutable OCI image digests. Write a size-bounded canonical manifest listing hashes and lengths for read-only boot/data media; an independent trusted-main bootstrap/gate (not target PR code) verifies **raw bytes**, manifest and image identity before guest execution. No Docker daemon or guest root workload runs on persistent `Yuz.local`. Guest receives a prebuilt, verified offline Engine package + immutable OCI image archive; no guest network fetch or `apt update` from external mirrors. A normal signed Ubuntu APT chain is sufficient; a bespoke C6 ten-deb fetch/mirror approval loop is not required.

**Provenance stop:** existing platform digest for `ubuntu:26.04` is a public manifest candidate; not a final project SSH image signer. Current `Dockerfile.proposed` deliberately exits 78 and is *not* a deployable image. Do not stage/start trusted code without separately approved byte provenance, isolated build and ephemeral keys. Native trusted-main orchestration never takes a target-defined verifier as its root authority.

## Directional network isolation and real A01–A03

Inside the no-NIC guest, Docker-internal bridges are **bidirectional** even with `internal: true`. A trusted guest-owned stateful forwarding filter is required **before** sshd admits connections. Pick the effective guest `nftables`/iptables-DOCKER-USER/bridge filter hook **based on observed kernel packet traversal**, not just a configuration string. Verify rule order/counters against Docker's forwarding, bridge-nf and conntrack modes and reject any unsupported or bypassed path. Never depend on a container's ability to alter host packet filters.

| Observed packet direction | `NEW` | `ESTABLISHED` | Must prove |
| --- | --- | --- | --- |
| MCP→node01/node02 TCP/22 | **ALLOW** only server-selected SSH targets | **ALLOW** | Both actual pinned-host-key SSH positive requests |
| Node01/node02→MCP TCP/8000 | **DENY** | **ALLOW only replies to real MCP-initiated sessions** | Raw TCP and spoofed auth attempts from both compromised-node identities fail |
| node01↔node02 | **DENY** | No unsolicited established session | No cross-node services/data/key access |
| nodes→guest host/LAN/internet | **DENY** | Only specifically reviewed replies | No route/device beyond no-NIC guest; no packet egress to persistent host |
| outside→guest control or SSH | **DENY** | No unsolicited state | `-nic none`, no QEMU guest-forward, no host-bound ports |

**A01–A03 evidence** (on authorized guest Engine, never synthetics): real sshd+fixed sudo launcher+agent+manager, identity/cap/NNP/FD and cgroup memberships, two distinct host key pins, MCP→SSH positive reads and negative wrong key/command/PTY/forwarding, manager failure, denied self-migration, bad cgroup delegation, denied node→MCP reverse TCP/8000, denied node↔node and guest outward, audit-before-effect failure and cleanup/restart. Record exact source SHA/OCI digest, immutable guest-media trust receipt, run IDs, observed counters and typed result exit; **do not** conflate offline contract tests with the live evidence.
