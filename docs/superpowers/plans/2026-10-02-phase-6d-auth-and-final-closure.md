# Phase 6D Portal Auth and Final Closure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Close Phase 6 by making the production application image reproducible, documenting interactive/headless Portal authentication and multi-profile operation, and proving all deployment security acceptance criteria before merge.

**Architecture:** First remove the only deferred technical gap by pinning the Python base image and every build/runtime dependency, then require two independent no-cache Linux/amd64 builds to produce the same image ID. Next extend the operator guide with Managed OAuth, Access service-token, Gateway/DLP, and separate-deployment profile patterns without adding any caller-to-profile authority. Finally run one cross-slice adversarial review over Phases 6A–6D and record closure evidence in the approved Phase 6 spec/development plan.

**Tech Stack:** Python 3.13.16 slim-bookworm pinned OCI digest, hash-locked Python wheels, Docker BuildKit/buildx, Cloudflare MCP Portal/Access/Gateway, pytest, self-hosted Ubuntu 26.04 x86 CI, authorized Mac x86 Docker host.

## Global Constraints

- Exact merged base is `ea836b804d913c3b043b0bec8641ce49ecff080e`.
- Phase 6D does not mutate a live Cloudflare account.
- One ssh-over-mcp process still owns exactly one operator-selected `SSH_OVER_MCP_PROFILE`; Cloudflare identity, OAuth claims, service-token identity, headers, query values, and tool arguments cannot select or override it.
- Interactive clients use Portal Managed OAuth; headless clients use Access service tokens. Neither credential is the Portal-to-origin bearer or the Tunnel token.
- Service-token access requires matching `Service Auth` policy at both the Portal Access application and each linked MCP-server Access application, with `Require user auth` off / `on_behalf=false` for servers reachable by that token.
- Gateway HTTP logging/DLP is defense-in-depth for real-time Portal tool traffic, not application authorization/audit; DLP AI prompt profiles do not apply to MCP Portal traffic.
- Multi-profile operation uses separate MCP deployment instances/private hostnames/origin bearers, never request-driven profile switching.
- The application production image must become bit-reproducible for the supported reference platform `linux/amd64`.
- Pin the Python base index digest to `python:3.13-slim-bookworm@sha256:5024f48ba9441d4b13a95d3945abc6365538e3a31109833367a1923523c6efed`; current linux/amd64 child manifest is `sha256:88310c082760d93ac7c74d579e95e53a4ab6ea52dd8901abc61a103daf488ac4`.
- Lock all Python build and runtime dependencies to exact versions with SHA-256 hashes; Docker builds may not resolve dependency ranges from the network.
- Use fixed `SOURCE_DATE_EPOCH=315532800` (1980-01-01 UTC) for image/wheel build steps.
- Keep the existing non-root `10001:10001`, no-public-port, Ledger authority, cloudflared secret/network, approval, audit, and mutation-uncertainty boundaries unchanged.
- CI remains only `[self-hosted, linux, x64, ssh-over-mcp-mac-x86]`; do not add a GitHub-hosted runner or Docker socket to CI.
- Final closure requires exact PR-head CI and exact merge-main push CI on Python 3.13/3.14, plus all Mac x86 live deployment probes.

## Review Focus

- A lock file that pins direct packages but lets transitive/build dependencies float is not reproducible; Task 1 must reject every un-hashed or non-exact dependency consumed by Docker.
- Two no-cache builds can still differ because of timestamps, generated bytecode, user-account metadata, or BuildKit attestations; Task 1 must compare full image IDs and rootfs layer digests, not only installed package versions.
- A headless service token must never be described as a replacement for the origin bearer or as a source of ssh-over-mcp profile authority; Task 2 owns explicit negative documentation tests.
- A portal containing multiple static-profile upstreams must not imply that one caller can choose a privileged profile through headers/tool input; Task 2 owns the separate-instance/private-hostname pattern and tests.
- Final closure must not rely on prose alone: every one of the 20 Phase 6 acceptance criteria and carried Phase 5 invariants needs an executable/static evidence pointer or an explicit external exact-head CI/live-test gate. Task 3 owns the evidence matrix.

### Task 2: Document Portal authentication, service tokens, and multi-profile operation

**Files:**
- Modify: `docs/cloudflare-deployment.md`
- Create: `tests/ops/test_phase6d_auth_guidance.py`

**Interfaces:**
- Produces operator guidance only; no Cloudflare account automation and no new application identity/profile interface.

- [ ] **Step 1: Write RED Managed OAuth documentation tests**

Require the guide to state:
- interactive/non-browser MCP clients authenticate to the Portal through Managed OAuth using the standard OAuth 2.0 authorization-code flow;
- Managed OAuth is enabled by default for new MCP portals as of the current provider behavior, and existing portal Access applications can enable it under Advanced settings;
- Managed OAuth applies to the Portal Access application, not to ssh-over-mcp's origin bearer;
- successful Cloudflare login does not select `SSH_OVER_MCP_PROFILE` or bypass application policy/approval.

- [ ] **Step 2: Write RED service-token documentation tests**

Require exact headless flow:
- create an Access service token;
- add matching `Service Auth` policy to the Portal Access application;
- add matching `Service Auth` policy to every linked MCP-server Access application the bot should reach;
- turn `Require user auth` off / `on_behalf=false` on those Portal server mappings;
- caller sends `CF-Access-Client-Id` and `CF-Access-Client-Secret`;
- upstreams still requiring per-user OAuth are excluded from service-token sessions;
- client ID/secret remain in caller secret storage and never in repository files, model prompts/tool arguments, MCP/container environment, or application logs.

- [ ] **Step 3: Pin the four-credential distinction**

Docs/tests must distinguish:
1. Tunnel token — authorizes cloudflared replica;
2. origin bearer — Portal to private ssh-over-mcp origin;
3. Access service-token ID/secret — headless client to Portal/Access;
4. Cloudflare API token — optional administrative API automation credential, not used by the runtime reference.

No credential may be documented as interchangeable.

- [ ] **Step 4: Add multi-profile deployment guidance**

Require:
- one deployment instance = one static `SSH_OVER_MCP_PROFILE`;
- materially different profiles use separate Compose project/service instances, private hostnames, and origin bearers;
- a Portal may aggregate those separate upstreams, but the caller never supplies a profile selector to ssh-over-mcp;
- per-user OAuth claim-to-profile mapping remains deferred beyond Phase 6;
- high-privilege upstream visibility should be controlled with Cloudflare Access/Portal policy plus ssh-over-mcp's independent static profile/policy, not request headers.

- [ ] **Step 5: Complete Gateway/DLP operational guidance**

Document:
- Gateway-routed real-time calls appear in Gateway HTTP logs;
- HTTP/DLP policies may inspect/block matching real-time upstream traffic;
- DLP AI prompt profiles do not apply to MCP Portal traffic;
- optional Logpush/SIEM export is Cloudflare observability, not a replacement for Security Ledger execution audit;
- background credential/capability sync is not equivalent real-time Gateway inspection;
- application policy, approvals, host-agent/OS policy, and audit remain authoritative.

Run docs tests and Ruff; commit:
```bash
git commit -m "Docs: add Phase 6D Portal auth operations"
```
