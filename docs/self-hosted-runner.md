# Self-hosted Linux security runner

This project needs Linux behaviors which ordinary hosted CI may not expose
reliably: `fork()`, fd-based exec, rlimits, and delegated cgroup v2.

The repository therefore keeps normal CI separate from a dedicated
self-hosted security-validation workflow.

## Security model

The security runner MUST:

- be dedicated to this repository;
- run as a non-root service user;
- have no passwordless sudo and no host secrets;
- use cgroup v2;
- receive only a delegated `cpu memory pids` subtree;
- use the custom runner label `ssh-over-mcp-security`;
- run the security workflow only through manual `workflow_dispatch`;
- keep the workflow source on trusted `main`;
- use a read-only GitHub token and no repository secrets;
- pin every third-party/action dependency in the privileged workflow to a full
  commit SHA.

The workflow accepts a target `ref` to test, but it refuses to start unless
the workflow itself was launched from `main`. This prevents a feature branch
from changing the privileged validation workflow and then scheduling that
changed workflow on the security runner.

A target ref still contains executable repository code. Treat manually
selecting a ref as an explicit trust decision.

## Recommended host

For the first working runner:

- dedicated Ubuntu 24.04 VM;
- x86-64;
- systemd 254 or newer;
- unified cgroup v2;
- at least 2 CPUs / 4 GiB RAM;
- outbound HTTPS access to GitHub;
- no inbound service required.

Use a dedicated account, for example:

```bash
sudo useradd --create-home --shell /bin/bash gha-ssh-mcp
```

Do not add this user to `sudo`, `docker`, `lxd`, or other groups which
effectively grant host-level privilege.

## Register the repository runner

Open:

```text
Repository → Settings → Actions → Runners → New self-hosted runner
```

Choose Linux/x64 and use the download/install commands generated by GitHub.
The generated registration token is short-lived; do not commit it or place it
in repository secrets.

When running `config.sh`, add the project-specific label:

```bash
./config.sh \
  --url https://github.com/zhangyuz/ssh-over-mcp \
  --token '<one-time-registration-token>' \
  --name 'ssh-over-mcp-sec-01' \
  --labels 'ssh-over-mcp-security' \
  --unattended
```

GitHub automatically provides the normal self-hosted OS/architecture labels;
the workflow additionally requires `ssh-over-mcp-security`.

## Install the runner as a non-root systemd service

From the runner installation directory:

```bash
sudo ./svc.sh install gha-ssh-mcp
cat .service
```

The `.service` file contains the actual systemd unit name.

Create a systemd drop-in:

```bash
sudo systemctl edit "$(cat .service)"
```

Use:

```ini
[Service]
Delegate=cpu memory pids
DelegateSubgroup=runner
NoNewPrivileges=yes
LimitCORE=0
```

The same example is stored in
[`../ops/actions-runner-cgroup-delegation.conf.example`](../ops/actions-runner-cgroup-delegation.conf.example).

Then reload and restart:

```bash
SERVICE="$(cat .service)"
sudo systemctl daemon-reload
sudo systemctl restart "$SERVICE"
sudo systemctl status "$SERVICE"
```

`DelegateSubgroup=runner` is important. It keeps the runner processes in a
leaf subgroup and leaves the service's delegated root available as an inner
cgroup where the project can create per-execution sibling cgroups.

The job must never receive write access outside that delegated service subtree.

## Validate the service locally

Confirm the runner is not root:

```bash
ps -o user,pid,cmd -C Runner.Listener
```

Inspect the unit:

```bash
SERVICE="$(cat .service)"
systemctl cat "$SERVICE"
systemctl show "$SERVICE" -p User -p Delegate
```

Watch runner logs with:

```bash
sudo journalctl -u "$SERVICE" -f
```

## Run the repository validation

After this runner configuration is merged to `main`:

1. Open **Actions**.
2. Select **Self-hosted security validation**.
3. Choose **Run workflow** from `main`.
4. Enter the branch, tag, or commit SHA to validate in the `ref` input.
5. Run it.

The job routes only to:

```yaml
runs-on: [self-hosted, linux, x64, ssh-over-mcp-security]
```

The preflight fails unless:

- the runner UID is non-root;
- the current cgroup ends in `/runner`;
- the parent delegated cgroup exposes `cpu`, `memory`, and `pids`;
- `cgroup.subtree_control` is writable;
- a temporary child cgroup can be created;
- `cgroup.procs`, `cgroup.kill`, `memory.max`, `pids.max`, and
  `cpu.max` are writable.

Only after that preflight does the workflow check out the selected target ref,
install the project, and run the test suite. The checkout and Python setup
actions are pinned to full commit SHAs rather than movable major-version tags.

## Persistent runner vs ephemeral runner

A persistent dedicated VM is acceptable for initial bring-up because this
repository is private and the workflow is manual-only. It should still be
treated as disposable infrastructure.

The preferred steady-state design is an ephemeral runner:

```bash
./config.sh \
  --url https://github.com/zhangyuz/ssh-over-mcp \
  --token '<one-time-registration-token>' \
  --labels 'ssh-over-mcp-security' \
  --ephemeral \
  --unattended
```

An ephemeral runner processes one job and is automatically deregistered.
The VM/container itself should then be destroyed or reset before another
runner is registered. For larger scale, use JIT runners or an autoscaling
runner implementation.

Do not simply re-register an ephemeral runner on the same dirty filesystem and
call that isolation.

## Why this is separate from normal CI

The existing `CI` workflow should remain on GitHub-hosted runners for normal
unit tests.

The security runner is intentionally separate because cgroup delegation is a
privilege boundary. Automatically running arbitrary pull-request code on that
runner would give PR code access to the delegated cgroup subtree and a
persistent runner account.

The self-hosted workflow is therefore a manually invoked validation gate, not
a generic PR executor.
